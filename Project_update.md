# Data-Generation Update: Consistent Goal Placement Across `k`

## 1. Summary

The experimental campaign sweeps a goal-count parameter `k = 1, 2, 3, 4`,
intended as a single difficulty axis: more goals, placed by the **detour
index**, should mean a harder exploration problem. In the current data
generation pipeline, `k = 1` does not follow this scheme — it silently
falls back to a structurally different goal, which breaks the axis at its
first point and, as shown in §3, is a plausible cause of at least one
documented anomaly in `notebooks/report.md`.

**Decision**: `k = 1` will be changed to use detour-based placement, like
every other `k`, instead of the current fallback. `src/goal_placement.py`
already supports this with no modification — see §5.

## 2. Current behaviour of the `k = 1` case

Both headless batch runners special-case `k = 1` as a caller-level
convention, bypassing goal placement entirely:

- `experiments/run_batch.py`, `_resolve_goals()` (lines 86–100): for
  `k == 1` returns `(None, None)` — no call to `scenario_goals()` — so
  `BaseAlgorithm` is constructed with `goals=None`.
- `experiments/01_experiment.py`, `main()` (the `-k/--k-goals` sweep,
  around lines 223–228): the same convention, independently implemented.

With `goals=None`, `BaseAlgorithm._resolve_goals()`
(`src/algorithms/base_algorithm.py:106-137`) falls back to the **default
goal**: the maze's 4-cell centre area, a fixed convention taken from
standard Micromouse competition rules (also the default `run.py` falls
back to when no `--goal`/`--n-goals`/`--auto-goals` flag is given at all).
Both `AStarExplorer` and `DStarLiteExplorer` additionally treat this case
as satisfied by reaching **any one** of the 4 cells (`_is_default_goal`,
checked in `astar.py:297` and `dstar_lite.py:619`), not all of them —
`BaseAlgorithm.goal_count` (`base_algorithm.py:85-92`) reports this case
as a single goal for exactly this reason, even though 4 cells are
resolved internally.

`src/goal_placement.py` itself has **no** special case for `k = 1` — its
own docstring (lines 32-38) is explicit that treating `k = 1` as the
default goal is "a convention of those callers, not something this module
special-cases," and `tests/test_goal_placement.py` (`test_nesting_from_k1`,
`test_k1_matches_first_goal_of_larger_scenario`) confirms
`scenario_goals(..., 1)` already returns exactly the first placement step
of any `k ≥ 2` scenario. The gap is entirely in the two experiment
scripts' own `k == 1` branches, not in the placement algorithm.

## 3. Why this breaks the difficulty axis

For `k ≥ 2`, goals are chosen to maximise the detour index
`detour(ref, c) = d_BFS(ref, c) / d_Manhattan(ref, c)` — cells that
*look* close but are actually far, which defeats a planner working from a
partial map (`docs/implementation_roadmap.md`, Phase 4). `k = 1` currently
opts out of this on three independent axes at once, not just one:

1. **Placement mechanism.** The centre cells are a fixed geometric
   location, uninformed by wall structure or by the detour index —
   nothing about them is "deceptive" to a partial-map planner.
2. **Goal count and termination semantics.** The default goal resolves to
   4 cells with **OR** semantics (stop at the first one reached); a
   genuine `k = 1` scenario is 1 cell. This is different in kind from the
   `k ≥ 2` scenarios, which require reaching **all** placed goals in
   sequence (**AND** semantics, remaining-goal set shrinks one at a time —
   see `astar.py:302-348` and `dstar_lite.py:532-654`).
3. **Spatial distribution.** The detour index is known to reward small
   Manhattan denominators, which clusters `k ≥ 2` goals *near the start*
   (documented in `docs/detour_metric_limitations.md` and §5.3 of
   `report.md`). The centre area, by construction, sits at the maze's
   geometric middle — typically far from the start cell `(0, 0)` — which
   is the opposite bias.

Because of this, `k = 1` is not simply "the easiest point" on a
difficulty axis defined by the detour index — it is a different
experimental condition altogether, placed on the same axis by
convention only. Nesting across `k` (each scenario's first `L` goals
equal the `L`-goal scenario's goals — `report.md` §1.3) also does not
hold in practice between `k = 1` and `k = 2` under the current
convention, even though `scenario_goals()` guarantees it for every
`k ≥ 1` internally.

Consistency, not increased absolute difficulty, is the actual
justification for the change: §5.3 of `report.md` already documents that
the detour index is a *relative* deception measure, not a calibrated
difficulty score, so `k = 1` under detour-based placement would not have
been a harder scenario than the centre-area default in any absolute
sense either. What it gains is being generated by the same deterministic
algorithm, on the same spatial-bias profile, as `k = 2, 3, 4` — turning
`k = {1,2,3,4}` into one coherent nested family instead of "one
special-cased scenario plus a three-scenario family."

## 4. Cross-check against `report.md`'s documented anomalies

`report.md` (generated from the current, inconsistent data) attributes
several anomalies to `k = 1`. Checked against the actual implementation:

- **§4.6 ("D\*-Lite's memory profile is structurally different at
  `k = 1`")** — the report's proposed mechanism ("with one goal that
  initial search must cover much more of the maze; with four, it stops
  early") does not match the code: at the current `k = 1`,
  `DStarLiteExplorer` seeds `rhs = 0` for **all 4** centre cells
  (`self._remaining_goal_set = set(self._goals)`, `dstar_lite.py:484`),
  exactly as many seed cells as `k = 4`. Goal *count* is not what differs
  at `k = 1`. The far more likely explanation, consistent with §5.3's
  documented start-clustering bias, is goal **position**: D\*-Lite's
  initial backward search stops as soon as it reaches the start, so
  centre-area goals (far from `(0, 0)`) force that search to cover much
  more of the maze than near-start detour-placed goals do. This
  observation should be re-derived, not reused, once `k = 1` uses
  detour placement.
- **§4.1 (A\* wall-clock time contradicts node counts at `k = 1`)** — the
  report attributes this to a warm-up/measurement artefact tied to
  execution order (`k = 1` is run first for every maze, per
  `GOAL_COUNTS = (1, 2, 3, 4)` in `run_batch.py`). This is independent of
  which goal-placement mechanism `k = 1` uses, so it will most likely
  persist after the change and should not be assumed fixed by it.
- **§4.3 ("`k` is not a monotone difficulty axis")** — the reported dip
  from `k = 1` to `k = 2` is measured against the centre-area default at
  `k = 1`. Once `k = 1` is detour-placed, this comparison no longer has
  the same inputs and must be recomputed; the current numbers cannot be
  assumed to still hold, in either direction.

This assessment is provided as background for the reanalysis in §7; it is
not a request to edit `report.md` now (see §6).

## 5. Scope of the change

**Changes:** the goal-count sweep in the two experiment scripts should
resolve `k = 1` via `scenario_goals(wall_matrix, width, height, start, 1)`,
the same call already used for `k = 2, 3, 4`, instead of `goals=None`.
`src/goal_placement.py` requires no change — it already treats `k = 1` as
the first step of the same algorithm (§2).

**Not in scope:** `BaseAlgorithm`'s default-goal fallback (`goals=None` →
4-cell centre area, OR-semantics termination) is a general, independent
feature — it is what `run.py` still falls back to when invoked with no
`--goal`/`--n-goals`/`--auto-goals` flag, and is unrelated to the
experiment scripts' `k`-sweep convention. It must remain in
`base_algorithm.py`, `astar.py`, `dstar_lite.py`, and every doc that
describes it as a standalone feature (`docs/mms.md`,
`src/algorithms/README.md`, `src/metrics/README.md`, `tools/README.md`,
`docs/implementation_roadmap.md` Phase 3d/5, and the `BaseAlgorithm`/
`run.py` entries of `docs/repo_structure.md`). Only the mention of it as
**`k = 1`'s meaning in a goal-count sweep** is in scope.

## 6. Editorial constraints for the update

- Every file identified in §7 as "update" should be edited to describe
  the new behaviour directly, as if it had always worked this way — no
  changelog language, no "previously k=1 used the default goal" notes.
  This matters because these files may be read by an LLM in a later
  step, and any trace of the prior convention risks being treated as
  still-current behaviour.
- `notebooks/report.md` stays untouched at this stage (§4 is the intended
  use of it: input to the reanalysis, not a file to edit).
- `notebooks/data_analysis.ipynb` needs no code change — confirmed
  `k`-agnostic by inspection (it reads `goal_count` from the exported
  JSON and never branches on its value). No comment in it references the
  `k = 1`-as-default-goal convention. (Note: the earlier draft of this
  document referred to a `data_analysis.py`; no such file exists — the
  notebook is the only analysis artifact.)
